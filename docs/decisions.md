## Phase 0

- **Next.js 16.3.8 instead of 16.2.x (deviation).** The latest stable Payload 3.x is 3.90.2, and `@payloadcms/next@3.90.2` declares `next: >=16.3.3 <17` as a peer dependency, so 16.2.x is unsupported. `create-payload-app@3.90.2` pins 16.3.3; we use the latest patch in that line (16.3.8). Spec §0.5: follow the library.
- **Payload 3.90.2.** Payload 4 is in beta (`4.0.0-beta.1`); stay on 3.x until 4 is stable.
- **pnpm 12.** The local toolchain is pnpm 12.4.1; `packageManager` pins it so CI uses the same version. pnpm 12 blocks dependency build scripts unless approved: `pnpm-workspace.yaml` → `allowBuilds` lists `esbuild`, `@swc/core`, `unrs-resolver`, `@parcel/watcher`.
- **Postgres 17** (`postgres:17-alpine`) for dev and CI; spec requires 16+.
- **Build without a database works with plain `next build`.** With `SKIP_DB_AT_BUILD=1` the `[locale]` layout's `generateStaticParams` returns `[]`; Payload routes are dynamic and don't touch the DB at build. Payload's "experimental build mode" fallback was not needed.
- **`prodMigrations` wired from day one** with an initial migration (`src/migrations/`). Development still uses schema push.
- **Shadcn `input` maps to `border-strong`, not `border` (deviation).** Spec §5.2 maps shadcn's `border` and `input` to `--border`, and also requires input borders to reach 3:1. Making every divider 3:1 would make the layout heavy, so `--border` stays a soft divider and `--input` → `--border-strong`, which is checked at 3:1. Spec intent (input borders ≥ 3:1) is kept.
- **Contrast pairs checked by `tokens:build`** (both themes): `fg` and `fg-muted` on `bg`, `bg-subtle`, `surface`, `surface-raised` ≥ 4.5; `fg-inverse` on `fg` ≥ 4.5; `primary-fg` on `primary` and `primary-hover`, `brand-accent-fg` on `brand-accent`, each status `-fg` on its status ≥ 4.5; `border-strong`, `ring`, `fg-subtle`, `primary` on `bg` and `surface` ≥ 3.
- **Scale generation.** Each seed's hue and chroma are kept; lightness follows a fixed curve per step (50 → 950, neutral 0 → 1000) so contrast stays predictable when seeds change. Colors are gamut-mapped to sRGB with culori's CSS Color 4 algorithm and emitted as hex.
- **Non-color tokens.** Radius, easing, durations and shadows are emitted in `@theme static` (they share Tailwind's `--radius-*`, `--ease-*`, `--shadow-*` namespaces, which are reset first). Shadow strength differs per theme through `--shadow-color-{sm,md,lg}`.
- **next-intl `alternateLinks: false`.** The middleware would otherwise send hreflang `Link` headers for every page; spec §6 emits hreflang only for `hiStatus = ready` pages (Phase 3).
- **Proxy matcher** excludes `/admin`, `/api`, `/go`, `/feeds`, `/_next`, `/_vercel` as whole path segments (so a future `/goals` page is still localized) and any path with a file extension.
- **Known dev-only warning:** React 19 logs "Encountered a script tag while rendering React component" for `next-themes`' inline theme script. The script runs from the server HTML (no flash); the warning doesn't appear in production. Revisit if `next-themes` ships a fix.
- **Dev admin credentials** live only in the gitignored `.env` (`DEV_ADMIN_EMAIL`, `DEV_ADMIN_PASSWORD`); the Phase 1 seed will use them.
- **Windows dev:** `next.config.ts` keeps Payload's `sassOptions.loadPaths` workaround for Turbopack on Windows.

## Phase 1

- **Collection slugs are kebab-case** (`legal-pages`, `short-links`, `data-requests`, `audit-log`, `daily-stats`, globals `site-settings`, `navigation`); the spec's camelCase names map 1:1. REST paths follow (`/api/legal-pages`).
- **Owner-only publishing** (releases, legal pages) uses two layers: create/update access that rejects `_status: 'published'` for non-owners (also hides Publish/Unpublish in the admin), plus a `beforeOperation` hook that lets non-owners only write with `draft: true`. Access alone is not enough: Payload writes the live row on any update without the draft flag, even when the body has no `_status`. Editors still see "Revert to published" and bulk publish buttons; clicking them returns 403.
- **`published` on releases is Payload's `_status`** (drafts). Unpublishing a release (Owner) removes it from the update feed.
- **Revalidation paths include the locale.** English URLs are rewritten to `/en/...` by next-intl, so hooks revalidate `/en/...` and `/hi/...`; pattern revalidation must include the route group (`/(frontend)/[locale]/...`), not `/[locale]/...` as spec §4.3 says. `revalidateTag` takes `{ expire: 0 }` (Next 16 requires a second argument). Hooks skip on `req.context.disableRevalidate` and swallow the "static generation store missing" error that next/cache throws outside a Next request (seed, tests, jobs).
- **SEO fields come from `@payloadcms/plugin-seo`** with `tabbedUI` on pages, products, services and posts, so those collections start with a `tabs` field. The plugin's meta title/description/image are localized automatically.
- **Storage:** R2 via `@payloadcms/storage-s3` only when `S3_ENDPOINT` and `S3_BUCKET` are set; local disk otherwise. `alwaysInsertFields: true` keeps the DB schema identical in both modes so migrations don't drift. Public files get CDN URLs (`NEXT_PUBLIC_CDN_URL`, `DOWNLOADS_BASE_URL`). The private bucket arrives with `privateFiles` in Phase 4.
- **Installer files are immutable.** Replacing the file of an installer is rejected through the API (any role): a published release must keep shipping the bytes, SHA-256 and update signature the Owner approved. A new build is a new installer and a new release. An installer referenced by a release can't be deleted, and file facts (size, MIME type) are only ever set by the upload, never by API edits.
- **Installer uploads:** root upload limit raised to 512 MB with temp-file streaming. `.exe` is sniffed as `application/x-msdownload` and `.msi` as `application/x-cfb`; both are accepted, the extension is enforced in a hook, and the stored MIME type is normalized. Filenames stay globally unique (Payload appends `-1`); the storage prefix `downloads/{product}/{version}/` is set only when a file is uploaded.
- **Audit log** is a small plugin that appends hooks to every collection and global (skipping the log itself and `daily-stats`); entries are written in the same transaction. The spec's `collection` field is named `entity`, `at` is the built-in `createdAt`, and `actorEmail` snapshots the actor because the user relationship is cleared if the user is deleted. Summaries never include titles of leads, data requests, users or testimonials (emails, customer names): the log can't be edited or deleted, so personal data there could never be erased (spec §16).
- **Live-row tracking (`src/plugins/liveDoc.ts`).** For draft-enabled collections Payload passes the latest _version_ to afterChange as `previousDoc`, which may be an unpublished draft. A small plugin records the live row and whether the write only saves a draft (mirroring Payload's rule, so bulk "Publish many", which sends the draft flag with `_status: published`, counts as a publish); revalidation uses it (draft saves revalidate nothing; unpublish and slug changes expire the URL that was live) and so does the audit log (`[draft saved]` vs `[published → draft]`).
- **Localized `required` means "required in English" (`src/plugins/defaultLocaleRequired.ts`).** Payload validates `required` against the locale being saved, which would block saving partial Hindi or publishing from the Hindi admin, and makes non-draft locale columns NOT NULL. Spec §6 expects partial Hindi with English fallback, so the plugin makes those fields optional in the schema and applies `required` only when saving English or creating a document (a new document has no English yet), passing it through to Payload's own per-type validators. Side effect: the admin no longer shows a required asterisk on them.
- **Lead and data-request submissions are records.** Staff can change status, notes, assignee and record a marketing-consent withdrawal; the submitted fields and consent records ignore API edits (field-level update access), not just admin read-only inputs.
- **Legal pages keep every version** (`maxPerDoc: 0`), because the published texts are what visitors and buyers agreed to; other collections keep 50. The effective date is required on publish.
- **Media** accepts images (not SVG, which can carry scripts), MP4/WebM video and `.vtt` captions, checked by extension; `text/plain` is only in the MIME list because Payload can't sniff `.vtt`.
- **No Translation tab on products** (spec §10 lists one): `hiStatus` stays a top-level sidebar field as §6 says, so it works as a list column and filter and is visible on every tab. A Translations view is planned for Phase 11.
- **Only the Owner can unlock admin accounts**, so the login lockout also protects the Owner from other admins.
- **`daily-stats.date` is text `YYYY-MM-DD`** (IST business date) so the Phase 3 `INSERT … ON CONFLICT (date, kind, key)` upsert stays simple.
- **Tests use a separate `jainav_test` database** brought up to date with `payload migrate` in a Vitest global setup (dev schema push disabled via `PAYLOAD_MIGRATING`). `pnpm check:migrations` (also in CI) compares the config's schema with the newest migration snapshot, so a forgotten migration fails the build (spec §18.3).
- **Migrations were squashed** into one initial migration during Phase 1; nothing had been deployed. From the first deploy on, migrations are only ever added.

## Phase 2

- **New dependencies are pinned to releases at least two weeks old** (supply-chain cool-off): motion 13.4.6 (motion 14 was a week-old major), radix-ui 1.6.7, zod 4.6.5, react-hook-form 7.89.0, @marsidev/react-turnstile 1.6.1, @axe-core/playwright 4.13.0. pnpm 12's own `minimumReleaseAge` check also rejects same-day releases; never bypass it with exclusions.
- **Motion** loads lazily (`LazyMotion` + `domAnimation`, `m.*` components) and honours reduced motion globally (`MotionConfig reducedMotion="user"`); continuous effects also check `useReducedMotion()`.
- **No page transitions:** View Transitions are not in stable React 19.2 / Next 16.3, so per spec §5.6 they are skipped.
- **Theme tokens apply to nested `data-theme` wrappers** (light block on `:root, [data-theme='light']`, shadcn aliases re-declared on `[data-theme]`), so the styleguide shows light and dark side by side.
- **`/styleguide`** is on in development and 404s in production unless `ENABLE_STYLEGUIDE=1` (staging). It's `noindex`.
- **Playwright on this machine** uses the installed Chrome (`PLAYWRIGHT_CHANNEL=chrome` in `.env`): Playwright's own Chromium download hangs while extracting here.
- **TextReveal splits at whitespace, not at `Intl.Segmenter` word boundaries** (deviation from spec §3/§20). It is still word-based and never splits inside a Devanagari word, but segmenter boundaries also fall between "₹" and "1,00,000", between a quote and its word, and around non-breaking spaces; each piece is an inline-block, so those boundaries would let the animated headline wrap where the plain text cannot. Splitting where the text already has a breakable space keeps wrapping identical.
- **Initial JS budget (spec §15, ~180 KB gzipped):** the placeholder home page measured 210 KB with every Phase 2 provider loaded eagerly. Three changes bring it to ~181 KB before hydration (+11 KB of Motion features right after): the Radix toast UI loads with the first `toast()` call, Motion's `domAnimation` features load asynchronously (`LazyMotion features={() => import(...)}`), and next-intl precompiles ICU messages at build time (`experimental.messages.precompile`, next-intl 4.14), which drops the message parser from the client. Next.js + React alone are ~122 KB, so Phase 3 pages need to keep heavy client code (mobile menu, mega menu, forms) lazy.
- **`@radix-ui/react-slot` is overridden to 1.5.0** (`pnpm-workspace.yaml`). This is an exception to the two-week cool-off: it was 4 days old. Slot 1.3.3, which radix-ui 1.6.7 pins, unwraps only one layer of a lazy child. When a client component that uses `asChild` (MagneticButton, Radix triggers) gets its children from a Server Component, client navigation could crash with "Slot failed to slot onto its children". The package is 165 lines; its diff from 1.3.3 was read in full: an unwrap loop plus `aria-describedby` merging, no install scripts or network code. Overriding one package keeps the change much smaller than bumping radix-ui to 1.8.1, which changes 52 packages. Drop the override when radix-ui is bumped after its cool-off (from 2026-10-26).
- **LanguageSwitch uses `next/link`**, an exception to "use `@/i18n/navigation`". Given a `locale` prop, next-intl's Link forces a prefix (`/en/...`) so the proxy can set its locale cookie. Cookies and detection are off here, so that prefix would only 307-redirect, and English URLs have no prefix (§6). The href comes from next-intl's `getPathname`.
- **The header compacts on scroll with transforms only** (§8.1 + §14). The sticky box stays 4rem, the background scales to 3.5rem and fades in, the row moves up and the logo shrinks. Changing the box height would shift the page below it (CLS).
- **Hindi typography overrides theme variables.** The `:lang(hi)` rule lives in the base layer, which every `text-*`/`leading-*`/`tracking-*` utility beats. So it also overrides the variables those utilities read (`--text-*--line-height`, `--leading-*`, `--tracking-*`): Devanagari gets more line height at every size, scaled down for display sizes, and no tracking.
- **Spinner is a named image, not a live region.** A `role="status"` region that mounts together with its text is often not announced. Callers that need an announcement keep their own status region mounted and change only its text, as MultiStepForm does with "Sending…".
- **The `dark:` variant skips light islands** nested inside a dark page, the same way the theme tokens do.
- **Transition defaults come from the motion tokens.** `--default-transition-timing-function` and `--default-transition-duration` are generated, so a bare `transition-*` uses `ease-out` and `duration-fast`. The tokens build also fails if `--hover` equals a surface it sits on.

## Phase 3

- **Caching uses `unstable_cache` per read, tagged by collection** (Next's previous caching model). Cache Components stays off as spec §2 says: Payload's admin isn't built for it. Every public Local API read goes through `read()` in `src/lib/cms.ts`, keyed by locale and inputs and tagged with every collection it touches, so the existing hooks (one tag per collection) expire every page that used the data; `revalidatePath` still expires each document's own pages in both locales. Draft mode skips the cache, and so does development: dev renders every request anyway, and seeds and scripts can't expire tags.
- **Live preview uses Next.js draft mode behind the admin session**, with no shared preview secret. The admin's preview iframe opens `/api/v1/preview?path=…` (a site path only, validated), which checks the Payload session (staff roles) and enables draft mode. Pages then read drafts with that admin's own access (`overrideAccess: false` + `user`), and `RefreshRouteOnSave` re-renders after each save. The URL follows the admin's current locale, so Hindi previews show Hindi. Payload accepts the session cookie only with same-origin fetch metadata (its CSRF rule), which browsers send.
- **Site chrome lives in a `(site)` route group**, so `/styleguide` keeps its own frame. The 404 renders inside the site layout (`(site)/not-found.tsx`); the 500 page (`[locale]/error.tsx`) renders without the header because the layout itself may be what failed.
- **The catch-all `[...path]` route** serves block pages at `/{slug}` (About), then the redirects table (vanity `/vyro`, old URLs), then the 404 (spec §8.6). Next.js can only send 308 or 307 from a render, so redirect types 301/302 become 308/307 (same caching and method behaviour). Redirects keep the visitor's language prefix.
- **Redirects and short links are read with access off.** They are staff-only in the REST API (configuration, not content); the handlers only ever follow them.
- **Only the client namespaces of `messages` reach the browser** (`site`, `language`, `theme`, `ui`, `contact`, `system`). By default next-intl sends every message on every page.
- **FAQ uses native `<details>`**, not the Radix Accordion: closed Radix panels are unmounted, so answers would be missing from the server HTML; `<details>` keeps them and needs no JavaScript. FAQPage data is emitted with it.
- **Share images come from one route, `/og/{site|products/{slug}|blog/{slug}}.png`**, referenced by page metadata, instead of `opengraph-image` files: a page's own `openGraph` metadata replaced the file-based image of its segment, and product sub-pages inherited nothing. The `.png` path keeps the locale proxy out and lets Cloudflare cache it. Images are English only (spec §6) and use Satori's default font until the brand kit.
- **Company changelog filter is a route per product** (`/changelog/{product}`), so it works without JavaScript; this route is not in spec §7's table. **Blog pagination and tags are routes too** (`/blog/page/{n}`, `/blog/tag/{tag}`): reading query strings would make static pages dynamic. Tag pages show up to 100 posts without paging.
- **Deferred:** products hub filters (spec: only once there are more than six products); the scroll-linked FeatureScroller and the product hero animations (Phase 5 per §20: until then the hero shows its media or an accent panel with the logo); waitlist, contact, careers and start-a-project forms (Phase 4). Until Phase 4, "Join the waitlist" scrolls to a `#waitlist` section offering email, contact links preselect the product (`/contact?product=…`), and applications go by email.
- **A demo button with no scheduler link falls back to "Talk to us"** (contact), so it never renders a dead button.
- **Release channels are strict** (spec §12.5 "on that channel"): the beta feed and beta downloads see only beta releases. "Latest" is the highest semver, not the newest date.
- **Download counters** use the key `{product}@{version}` and the IST date. The public download total sums them and is cached for an hour (raw SQL writes bypass the hooks). The update feed answers 204 for unknown products and unparseable versions, 400 for malformed target, arch or channel, and is never cached, so unpublishing a release takes effect immediately. Installer URLs are absolute (local-disk URLs resolve against the request origin).
- **The contact map is Google's keyless embed, loaded on click.** The Phase 6 CSP needs `frame-src https://www.google.com`.
- **`company.businessHours` (localized) was added to site settings**: spec §8.9 shows business hours, but §9.2 had no field for them, and they must not be invented. Migration `20261016_041511_site_settings_business_hours`.
- **`pnpm seed:publish`** (development only; refuses non-local databases) publishes seeded drafts so local pages and e2e runs have content. Drafts that fail publish validation (MenuMesh without its URL, legal pages without an effective date) stay drafts.
- **Product docs are generated on first request**: static params cover only each docs index, because `generateStaticParams` can't use the draft-aware reads.
- **`/go/` rate limiting** moves to Phase 4 with the other rate limits (`rate-limiter-flexible`).
- **CI runs on `ubuntu-24.04`**: `ubuntu-latest` switches to Ubuntu 26 on 2026-10-19.
- **`server-only`** is resolved by Next.js itself (not a dependency); Vitest aliases it to Next's empty server build.
- **JS budget (spec §15): about 183–185 KB gzipped initial JS** on the measured pages (home, products, a product page, the blog), down from about 215 KB. Three changes got it there:
  - Scroll reveals (`Reveal`, `Stagger`, `TextReveal`) are CSS transitions on the motion tokens. They are driven by the same IntersectionObserver phase as before (`[data-reveal]` / `[data-stagger]` in globals.css).
  - `Tilt` and `MagneticButton` use a CSS transition instead of Motion springs.
  - Motion's `LazyMotion` provider moved out of the layout into the components that animate with Motion (today only `MultiStepForm`). Pages without such a component load no animation library. Phase 5 signature animations wrap themselves the same way.
  - The mobile menu dialog (Radix focus trap and scroll lock) loads on first use.
  - Remaining fixed cost: Next.js and React about 125 KB, the header's Radix NavigationMenu about 16 KB, next/image about 11 KB, tailwind-merge about 8.5 KB. A lighter desktop nav would bring it to about 175 KB (Phase 5 performance tuning).
  - Measured as the scripts the HTML references; the polyfill script is `noModule`, so modern browsers don't load it.
- **Maintenance mode answers 200**, not 503: a statically rendered layout can't set the status. The Phase 6 deploy (Caddy or the proxy) should serve a 503 with `Retry-After` while it is on.
- **Next.js quirk:** a render-time redirect (`/vyro`) repeats its identical `Location` header on the first, uncached response. Browsers accept identical duplicates, and cached responses have one header.
- **Long dev sessions can fail renders** with "context from NextIntlClientProvider was not found" after many hot reloads. A fresh `pnpm dev` (or removing `.next/dev`) clears it, and production builds are unaffected (the full e2e suite passed against `next start`).
- **Review follow-ups not done in Phase 3:** video caption language is fixed to English (no per-file language field yet); English-fallback `lang` marking is per page or block, so a few Hindi UI labels inside fallback blocks may inherit `lang="en"`.

## Phase 4

- **One forms endpoint, `POST /api/v1/forms/{form}`** (contact, project, waitlist, newsletter, careers, data-request), multipart: `data` (the fields as JSON, validated with the same Zod schemas the browser uses), `meta` (language, page, referrer, UTM, honeypot, Turnstile token) and `cv`. The pipeline keeps spec §13's order: Zod → Turnstile → rate limits → honeypot → save → notify. A filled honeypot answers like a success and keeps nothing.
- **Notifications run in `after()`**, not the Payload Jobs Queue: the lead is saved before the response, so a failed email or Telegram call loses an alert, never a lead (each is logged). Move them to the queue if alerts ever need retries.
- **Rate limits use `rate-limiter-flexible` on Postgres** in a schema of its own (`rate_limit.hits`, created on first use). Payload's dev schema push manages only `public`, so it never drops the table, and it needs no migration. Keys are an HMAC (keyed with `PAYLOAD_SECRET`; a plain hash of an IPv4 address or a known email is reversed by trying them all) of the IP (`CF-Connecting-IP`; IPv6 counted per /64, which one subscriber usually holds) or of the inbox (the address without a `+tag`; for Gmail also without dots). Limits: 10 form submissions per IP per 10 minutes (all forms together), 5 per email address per hour (this also caps auto-replies sent to someone else's address), 60 `/go/` clicks per IP per minute (429 with `Retry-After`).
- **Consent is a notice, not a checkbox** (spec §13 consent UI): leads record the notice version (`CONSENT_VERSION` in `src/lib/forms/schemas.ts`, bump it when the wording changes), the time and an HMAC of the IP. The marketing box is separate and unticked; subscribing to the newsletter is itself the marketing consent, counted once confirmed.
- **Duplicates:** a second waitlist sign-up for the same product and address, or a newsletter sign-up from an already confirmed subscriber whose consent stands, answers success without a new lead or email. A second waitlist sign-up that ticks the box records the consent on the existing lead (clearing a withdrawal); a newsletter sign-up after a withdrawal starts a new double opt-in.
- **Waitlist box is the launch-email consent.** Spec §13 sends "Email this waitlist" only to leads with marketing consent, so the waitlist form's box says "Email me when {product} is ready", and the success text and auto-reply promise that email only when it was ticked.
- **Newsletter tokens:** the confirmation token is random (256 bits), stored as sha256, single use and valid 7 days. Unsubscribe links carry the lead id signed with `PAYLOAD_SECRET`, so they work in every email ever sent without storing anything; rotating the secret breaks old links. Unsubscribing marks every lead with that address. The confirmation email already carries `List-Unsubscribe` / `List-Unsubscribe-Post`; Phase 9 marketing emails use `unsubscribeHeaders()` from `src/lib/tokens.ts`.
- **Confirm and unsubscribe act on GET** (the links spec §13 names). Email link scanners that follow links could confirm or unsubscribe someone; if that shows up, switch the GET to a page with a button.
- **No staff alert per newsletter sign-up** (noise); every other form emails the routed inbox and posts to Telegram. Routing: sales and partnership → sales, support → support, careers → careers, press and other → hello, project and waitlist → sales, privacy requests → privacy; a missing inbox falls back to hello, then `EMAIL_REPLY_TO`, else the email alert is skipped with a warning.
- **Auto-replies never repeat what the visitor typed** (not even the name), so the forms can't be used to send arbitrary text to someone else's inbox. Telegram alerts carry no personal data: the kind of submission, the product, a project's service and budget band or the job applied for, and the admin link.
- **Internal alert emails are English only**, a deviation from the Phase 4 task list ("templates (English / Hindi)"): spec §6 sends emails in the recipient's saved language, and the routed inboxes are plain addresses with no language (the admin is English too). Add `email.notification.*` keys if staff ever choose a language.
- **Hardening after review:** form bodies are counted as they are read (a chunked request has no Content-Length to check) and capped at the CV size plus 512 KB; failed saves log only the database error code, never its message (it lists every bound value); NUL characters are stripped from text (Postgres refuses them); the email check adds Payload's own rule so nothing that passes the form fails the save; a CV that fails the server's PDF check is reported on the CV field; private-file downloads (the file or its signed redirect) send `Cache-Control: private, no-store`, since Cloudflare caches `.pdf` paths by default; a lead deletes the files it lists as well as those naming it as owner; a form whose code fails to download shows a notice instead of the error page; a failed unsubscribe link lands on its own page with a way to ask by email or privacy request.
- **Known gap: R2 delete failures.** The storage plugin's afterDelete hook only logs a failed object delete, so deleting a lead can leave its CV in the private bucket. Making it fail the delete needs `@aws-sdk/client-s3` as a direct dependency (it is only installed through `@payloadcms/storage-s3`), which needs approval.
- **Emails without Resend:** development writes each email to `.outbox/` as JSON (a local test mailbox the e2e tests read); production drops it and logs an error. Payload's default console adapter would print personal data into the logs.
- **CVs** are PDFs up to 5 MB, checked by their bytes (header and trailer, the same check Payload's upload validation runs) and stored under a random name in `privateFiles`: local disk in development, the private R2 bucket in production through a second `s3Storage` instance with 5-minute signed downloads after Payload's access check. Deleting a lead deletes its files first (a `beforeDelete` hook: the database clears the file's owner link in the same delete).
- **Leads admin:** Payload's list view already gives filters (type, status, product, date) and bulk edit (status). Added: an "Export CSV" button (`/api/leads/export`, honours the current filters, search and sort; IST dates, UTF-8 BOM, spreadsheet-formula guard) and reply links (email, WhatsApp) in the lead sidebar.
- **The privacy request form sits on the `privacy-requests` legal page**, so it goes live when the Owner publishes that page (spec §8.13).
- **"Start a project" leads to `/services#start`**, where the five-step form is (spec §8.7); the contact page links there too.
- **JS budget:** classic Zod put about 90 KB into the browser. The shared schemas use `zod/mini` through `import * as z`; Turbopack keeps all of Zod for the `{ z }` export. The lead forms are code-split (`src/components/forms/lazy.tsx`): the server renders the full form, and its code (react-hook-form, Zod, Turnstile, about 40 KB) loads after the page's own JS. Until it hydrates the form's fieldset is disabled, because react-hook-form would reset anything typed earlier and a native submit would put the fields in the URL. The footer newsletter loads its form as it nears the viewport. Initial JS is now 187–189 KB on every measured page (home, products, product pages, contact, services, careers), up 3 KB from Phase 3 for the site-wide newsletter placeholder and WhatsApp button.

## Phase 5

- **Products menu without Radix.** The header's products menu is a hand-built disclosure (WAI disclosure navigation): a button and a panel, opened by click, Enter, Space or a mouse hover (a click then pins it), closed by Escape, an outside press, focus moving elsewhere, the mouse leaving a hover-opened panel, or navigation. Radix NavigationMenu put about 15 KB into every page's initial JS; initial JS is now 175–178 KB on every measured page (was 187–189).
- **Mukta is not preloaded.** Its four Devanagari weights (about 260 KB) were preloaded at high priority on every page, ahead of the CSS and scripts. Without preload, `unicode-range` loads only the weights a page's Devanagari text uses (one on English pages, for the "हिंदी" switch); Hindi pages swap the font in. This was the main Lighthouse LCP cost.
- **Gradient mesh is CSS.** Three blurred blobs drift on `transform` keyframes and lean toward a mouse pointer through two CSS variables; it pauses off-screen and in a hidden tab, has a CSS-only pause toggle (WCAG 2.2.2), and is still with reduced motion.
